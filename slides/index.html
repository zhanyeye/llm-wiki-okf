基础设施知识库怎么搭

先讲两套现成做法各自规定了什么，再讲本仓库怎么用它们。

  1. LLM Wiki：知识库怎么维护（Karpathy）
  2. OKF：文件怎么写、怎么组织（Google Cloud 的 Markdown 规范）
  3. 本仓库：目录、type、Agent 工作流、目前做到哪
1 / LLM Wiki · 要解决的问题

上传一堆文件再问，每次都是从头拼

常见做法

把文档丢进 RAG / NotebookLM / ChatGPT 文件。每次提问：检索片段 → 生成答案。问完，综合结论留在对话里。

后果

  • 没有一本「已经交叉引用过」的中间层
  • 新材料和旧说法冲突，不会被记下来
  • 下次同一问题再检索一遍

LLM Wiki 的改法：先把材料编译进一套长期维护的 wiki，提问时读 wiki，而不是每次打回原文。

1 / LLM Wiki · 三层

来源不动；wiki 由模型写；规则写在 schema 里

人管选材料、问什么、要不要留下某次分析。模型管摘要、改链接、改索引。wiki 当代码库用：git 出历史。

1 / LLM Wiki · 三个操作

入库会改很多页；查询从索引下钻；定期体检

Ingest读一篇来源 → 写/改 wiki 多页 → 更新 index → 追加 log。一篇材料动十来页是正常的。
→
Query先读 index.md 找相关页，再打开正文作答。有用的对比表、排查树可以另存成新页。
→
Lint查矛盾、过期说法、没有入链的页、提到了但没有专页的概念。

index.md

按类列出每一页：链接 + 一句话。规模大约一百个来源、几百页时，先读索引再打开文件，不必上向量库。

log.md

按时间记：哪天 ingest 了什么、问过什么、做过 lint。条目用固定日期前缀，方便 grep。

1 / LLM Wiki · 它没规定的

这是一篇方法说明，不是文件格式标准

  • 目录叫 entities 还是 systems，原文让你按领域自己定
  • 要不要 YAML、字段叫什么，原文当可选（Obsidian Dataview 用得到再加）
  • 搜索：中等规模靠 index；再大再上本地检索

所以还需要一层「文件怎么写才让人和 Agent 都能解析」——这是 OKF 管的。

2 / OKF · 是什么

知识包 = 一棵目录里的 Markdown + YAML

Open Knowledge Format。目标：人能直接打开文件，Agent 不用专有 SDK，git 能 diff。不分发平台、不绑定哪家模型。

Bundle

一整棵目录是分发单位。可以是 git 仓库，也可以是大仓库里的一个子目录（本仓库里是 wiki/）。

Concept

每个非保留名的 .md 是一个概念。路径去掉 .md 就是概念 ID。

子目录

只是分组，不是套娃 Bundle。链接 /系统与架构/minio.md 相对 Bundle 根解析。

2 / OKF · Bundle 长什么样

任意层都可以有 index.md；log.md 可选

根 index.md 可以写版本号。Agent 先读索引，再决定打开哪几篇，避免整包塞进上下文。

2 / OKF · 单篇文件

规范里唯一必填的 frontmatter 是 type

---
type: Playbook          # 必填，生产者自定取值
title: Helm 部署失败
description: 一句话摘要
tags: [helm, k8s]
status: draft           # draft | stable | deprecated
generated: { by: human:x, at: ... }
verified: { by: human:x, at: ... }
stale_after: 2027-02-17
sources: []
---

# 正文：标题、列表、代码块
见 [Rancher](/系统与架构/rancher.md)
  • type 用来过滤和套模板，不认识的 type 当普通概念，不要拒收
  • generated / verified：谁写的、谁核对过；没有 verified 就是未确认
  • stale_after：到了这天当过期，用绝对日期
  • 链接推荐以 / 开头，相对 Bundle 根，文件挪目录时比较稳
  • 允许加自己的字段（本仓库加了 domain owner services）
2 / OKF · 和 Wiki 怎么分工

一个管流程，一个管磁盘上的样子

LLM WikiOKF
回答什么谁写、何时写、查询从哪开始、怎么防止只停在聊天里文件布局、frontmatter、保留名、链接怎么解析
有没有强制 schema没有，靠一篇 schema 文档（AGENTS.md）几乎没有；必填只有 type
index / log建议有，给模型和人导航、对账保留文件名，格式写死了大概长什么样
本仓库怎么用ingest / query / lint 写在 Skillwiki/ 当作一个 Bundle
3 / 本仓库 · 对应关系

三层落到具体路径

wiki 正文只写运维内容。格式和流程不写进 wiki，避免知识库里掺说明书。

3 / 本仓库 · 目录

分组按「要干什么」，不按 k8s / 存储切顶层

wiki/
  index.md          分组清单（frontmatter 仅 okf_version）
  log.md            按日、最新在上
  资源注册表/        Registry     入口、负责人、告警；不写密钥
  系统与架构/        Architecture 拓扑、请求/数据链路
  操作手册/          Runbook / Configuration
  故障排查/          Playbook     按症状；值班先看这里的 index
  架构决策记录/      Decision
  常见问题/          FAQ
  规范与约束/        Policy
  案例与复盘/        Incident
  技能地图/          Curriculum   目前只有 index
  新人上手/          Onboarding   目前只有 index
  自动化脚本/        Automation   目前只有 index

原 00–08（镜像、k8s、网络…）放 frontmatter 的 domain。文件名英文短横线，中文只出现在 title。

3 / 本仓库 · 查询和入库

人和 Agent 走同一条路径

查

1 wiki/index.md看分组
↓
2 故障排查/index.md只知道现象时用；无文档标「待入库」
↓
3 打开 2–5 篇正文系统名 → 系统与架构；找进程 → 资源注册表

写（Skill infra-wiki）

  • query：按上面下钻；wiki 没有的集群名、步骤不要编
  • ingest：读 raw → 套 templates → 改相关页 → 更新 index 和 log
  • author：从零写也必须套模板，填 type 和 domain
  • lint：python scripts/okf_lint.py 查 frontmatter、type 是否落对目录、断链、过期
3 / 本仓库 · 现在有什么

框架可用；内网那约 80 篇还没迁进来

已经有

  • 11 个分组的 index、12 份模板、lint 脚本
  • 示例：MinIO / Rancher、找进程、磁盘满、绿区代理、Helm 失败、NFS 复盘、MinIO 决策
  • 示例是骨架，占位符用 <cluster>，没有编内网地址

还没做

  • 按值班痛点把手册/排查/注册表补全
  • 把内网旧文档一页一页套模板、打 domain、改链接
  • 技能地图、新人上手、自动化脚本目前空 index
  • 没有站点、没有向量检索
演示时可以打开的文件

从 wiki/index.md 往下点

  • 约定：AGENTS.md
  • 值班入口：wiki/故障排查/index.md
  • 一篇完整示例：wiki/操作手册/disk-full.md
  • 校验：仓库根执行 python scripts/okf_lint.py

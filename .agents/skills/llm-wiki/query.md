# query

**以 `wiki/` 为主，raw/ 为回退补充，查询只读**：不写任何文件（含 `index.md` / `log.md`）；需要落库或执行操作时，提议并转对应流程（ingest / execute）。搜索命中路径后再按需打开正文，不要一次性读整库。

## 搜索范围策略

1. **优先搜 `wiki/`**：OKF 格式的编译结果（frontmatter、type、tags 等结构化信息）
2. **回退搜 `raw/`**：当 wiki/ 无命中或命中结果不充分时，在 raw/ 中继续全文搜索
3. **两者都找不到**：才返回"未在 wiki 中检索到"

> 原始设计参考：[Karpathy LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)

## 流程

### 1. 理解问题

从用户原话提取检索词，保留原始报错和专名，不要求用户使用 `system:` / `tags:` 等特殊语法：

- 系统、组件、环境、资源名
- 症状、动作、期望结果
- 报错原文、错误码、日志片段
- 中文/英文写法、缩写、明显别名和词形变体

扩展词只用于召回页面，不能作为内网事实写进答案。问题缺少系统或环境信息时先检索；仅当不同解释会导致步骤明显不同时，再追问一个关键问题。

### 2. 导航与召回

1. 读 `wiki/index.md`（不是仓库根 `index.md`），了解当前分组。
2. 根据意图优先看可能的分组及其 `index.md`：
   - **现象不明 / 排障** → `wiki/故障排查/index.md`（若存在）
   - **是什么 / 公司怎么用 / 稳定约束** → 原子知识
   - **已知系统的跨实体链路 / 拓扑** → 系统与架构
   - **怎么操作 / 变更 / 回滚** → 操作手册
   - **哪一套 / 入口 / 负责人 / 环境 / 日志路径** → 资源注册表
   - **短报错 / 常见问法** → 常见问题
3. 分组导航不是硬前置。无对应 index、index 无命中、用户问题跨分组或措辞模糊时，直接在 `wiki/` 做全文召回，搜索：
   - 文件名、index 条目和 frontmatter：`id`、`title`、`description`、`aliases`、`tags`、`domain`、`asset_kind`
   - **正文全文**：用户原词、完整报错片段、拆分后的实体/症状词及其明显变体
4. 搜索不区分大小写；优先完整短语（如标题原词），再搜词组组合，最后才搜单个宽泛词。拆词/宽泛词命中只作候补，不得升格为并列候选。不要一次 Glob/Read 整库；搜索命中路径后再按需打开。
5. **回退机制**：`wiki/` 全文搜索无命中或命中结果不充分时，立即在 `raw/` 中继续全文搜索（不限于某一子目录）

### 3. 核验候选

1. 按以下顺序选择候选：标题/标签精确命中 > 报错或症状正文命中 > 多个关键词共同命中 > 单个宽泛词命中。已有高优先级精确命中且正文完整时，视为检索充分，低优先级命中不再展开。
2. 打开最相关的正文；没有相关页不要凑数。跨页回答时确认页面确实互补，不能只因同分组或同组件就拼接。问题含症状词（如「上传失败」「连接超时」「502」）时，用症状词过滤候选：**同系统/同组件但症状不同的页面不算互补**，不并列展开，最多在答案末尾作一行「相关页」提示区分。
3. 首轮命中后按问题需要沿**有类型的关系**定向展开，最多两跳：
   - Registry → `technology` 回到 Atomic，解释组件定义与稳定约束。
   - Runbook/Playbook → `operates_on`/`depends_on` 找具体资产和底层规则。
   - FAQ → `answers_about`；Decision → `decides_for`。
   - 问“谁使用/哪些手册受影响”时查 backlinks，派生反向关系，不要求页面双写 `used_by`。
   - 只打开能回答当前问题的目标标题/块；同批、同目录、同 domain 不作为扩展依据。
   首轮已有完整精确答案且用户未问上下游时停止，避免图遍历稀释答案。
4. 区分“命中页面”和“页面足以回答”：
   - wiki/ 有命中但正文没有具体步骤或完整信息 → **立即回退 raw/ 搜索**（不停止）
   - wiki/ 和 raw/ 都有内容时，wiki/ 不足的部分用 raw/ 补充，标注「⚠️ 原始内容，尚未编译」
   - 只有 wiki/ 和 raw/ 都无相关信息时，才说“未在知识库中检索到”
5. 检查 frontmatter：
   - 记录 `sources`（原始来源 URL）和 `raw/` 来源路径，供答案末尾溯源
   - 已过 `stale_after` → 标明「可能过期」
   - 没有 `verified` → 标明「未经人工确认」
   - `status: deprecated` → 不作为默认操作依据；如必须引用，明确标明已废弃
   - Registry 的 `source_of_truth` / `sync_mode` → 外部系统为权威源时提醒以其当前状态为准
   - 内容级引用只支持目标标题/块实际存在的链接；断链信息不进入结论

### 4. 覆盖度诊断

- `wiki/` 中除 `index.md`、`log.md` 外没有概念页 → **立即回退到 `raw/` 全文搜索**（可能包含未编译的原始文档）
- `wiki/` 无命中但 `raw/` 有相关内容 → 标注「⚠️ 原始内容，尚未编译」，引用作答并附 `raw/...` 路径；答案经用户确认有效后，必须再次主动建议按 [ingest.md](ingest.md) 编译为正式页（这是补库价值最高的时机）
- `wiki/` 和 `raw/` 都无命中 → 说“未在知识库中检索到”，简要说明搜过的分组与关键实体/症状词，并指出缺口类型（缺 Runbook 还是缺 Registry 页等），便于用户换词或安排入库

## 用户更正与页面冲突

- 用户指出页面内容错误、过期或与本环境不符时：先按更正后的说法回答，并提议把更正落库（流程见 ingest.md §用户更正）；不要让更正只留在聊天记录里。
- 两篇候选页相互矛盾时：两个结论都呈现并标注冲突；默认采信 `verified` 较新或 `stale_after` 较晚的一篇并说明理由；建议用户走 ingest 裁决合并。

## 输出标准

- 引用所用页面路径（对话中用仓根相对路径，如 `wiki/操作手册/页.md`）。
- 答案**末尾附源头链接**（单列「源头链接」小节，放在「依据与风险」之后）：优先取已引用页面 frontmatter `sources` 中的原始 URL（如 `https://wiki.huawei.com/.../WIKI...`）；raw/ 命中给 `raw/...` 相对路径；正文中的监控看板/部署地址按需附上。页面无来源记录时省略该节，**不要臆造 URL**。
- 区分「直接命中页」与「仅同系统相关页」：后者不并列成候选，最多一行「相关页」提示，避免同实体不同故障的页面稀释答案主体。
- 回答“是什么”优先引用 Atomic；回答“在哪一套”优先引用 Registry；回答“怎么做/怎么查/为什么”以 L2 为主并补其依赖的 L0/L1。不要用 Registry 代替组件定义，也不要用 Atomic 臆测生产部署。
- 命令、主机名、集群名、地址**只来自已打开的页**；页内占位符保持原样，不要替换成臆造值。页面依据与模型常识冲突时，以页面为准，并提示页面可能过期。
- 故障排查 index 中该项为「待入库」、或没有正文 → 回答「没有成文步骤」；可指出最接近的已有页，不要补全内网命令或主机名。
- wiki 里没有的事实 → 说「wiki 里没有」，建议走 ingest 流程补库；不要编。
- 排查树、跨页对比表、从 raw/ 综合出的结论：**必须**主动问是否回写成新页（用户同意后转 ingest §对话存档）。
- 答案详略与问题风险相称。简单入口/FAQ 可直接回答；排障、变更和操作问题默认组织为：
  1. **结论与适用范围**：当前最可能的判断，以及页面覆盖的系统/环境。
  2. **处理步骤**：按依赖顺序给出可执行步骤；正文没有的步骤明确标缺失。
  3. **验证与升级**：如何确认恢复、何时停止或升级；页面没写则直说。
  4. **依据与风险**：列出页面路径，并集中标注过期、未验证、已废弃等状态。
- 不要为了简洁省略正文已有的前置检查、验证、回滚或升级条件；也不要为套模板重复信息。
